WHAT MUST BE ATOMIC IN A FUTURE FIX
1. Every successful ring insertion publishes, under memory.lock after all row
   fields commit, a token (process-local ring epoch, monotonic write serial,
   actual slot index). Do not derive it later by reading tree.data_ptr outside
   that lock. Existing memory.add return behavior and agent.step integer-index
   API stay compatible: use a private/common commit implementation plus an
   opt-in token-returning ingestion API, executing each insert exactly once.
2. Async per-client episode/lookback bookkeeping retains the token from that
   same insert. Do not regenerate a token from a bare index at admission.
3. With N current successful writes, pointer p to next cyclic slot, capacity C,
   token serial s/index i is resident iff same epoch, 0<=N-s<C and
       i == (p - 1 - (N-s)) mod C.
   This follows exactly from one-slot cyclic advancement per successful write.
   It holds after arbitrary starting pointer and does not assume equal client
   rates or time-based throughput. At age C-1 it is resident; at C overwritten.
4. Under the SAME existing replay lock used by each copy/write, validate the
   tokens BEFORE range filtering, bank-span subsampling or any mutation. A
   separate validate-unlock-admit sequence is a TOCTOU bug. The current lock is
   plain non-reentrant: do not wrap _bank_admit in another acquisition; factor
   a private locked limb or place validation directly in its existing with.
5. Conservative policy for bank admission: if any supplied episode reference
   is stale/unknown/different epoch, refuse that admission and count the reason.
   Do not silently admit the remaining tail as a complete elite episode. If a
   later policy intentionally admits a partial tail, it requires explicit
   different semantics/metadata, not this correction. Both HOF and EpHOF share
   the validation. Normal fresh admissions keep all thresholds, per-game caps,
   relief clocks, scores, stride, copied fields and persisted bank formats.
6. Connected callbacks must validate their selected tokens under the same lock
   BEFORE boost_priorities, apply_pre_death_penalty or mark_interesting. A short
   lookback reduces exposure; it does not guarantee residency after a long
   cross-client delay. Preserve current duplicate/index selection semantics
   AFTER validity is established. Foreign rows must never be changed.

CAN THIS AVOID A SIX-MILLION-ELEMENT GENERATION ARRAY?
Yes, conditional on enforcing the write/epoch invariant above. Successful
inserts are globally serialized through memory.lock and advance the ring by
one. One epoch + one serial (optionally epoch's starting pointer) can derive
residency and slot index; no per-slot array is mathematically required. Tokens
must be genuine outputs of commit. The fixture models this invariant only; it
is NOT proof that a production implementation has established it.

The current _adds_total is a bank-age/insert-attempt clock, not yet a reliable
completed-write token. It increments at add422 BEFORE tree/row writes. A failed
conversion/copy can leave partial mutation. clear495-511 and flush2221-2244
reset ring pointer/contents WITHOUT resetting _adds_total in the held source;
load/adoption replace rows/pointer without incrementing it per row. Reusing it
unchanged is UNSOUND. Either add a dedicated tiny successful-write serial or
prove reuse with an epoch/base offset plus exception handling; never change its
existing bank starvation/quota semantics just to obtain a token clock.

PER-CLIENT STORAGE COST ALSO NEEDS MEASUREMENT
Naively keeping Python triples for192 x65536 references can cost substantially
more than a48MB uint64 per-slot array. No-array does not imply low total cost.
Possible compact representation: one epoch per uninterrupted client segment,
retain serial integers (and derive indices under lock), sharing references
between episode/lookback queues. Epoch change must mark/discard the old partial
segment rather than merge old/new serials. Preserve public integer-index APIs.
Packed bounded serial storage is another option, but select only after memory/
CPU measurement. No implementation or optimization is chosen by this design.
